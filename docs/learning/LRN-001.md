# Acceptance criteria as your first test

## Key Concepts

An **acceptance criterion** is a promise about your app written in a fixed shape:

> **Given** some situation, **When** someone does something, **Then** a specific result happens.

A **test** is that same promise turned into code that checks itself. "Then the
stored date is `2026-11-10`" becomes a line of code that *fails loudly* if the date
comes out differently.

**TDD (test-driven development)** simply reverses the order you might expect:

1. Write the check **first** — it fails, because the feature isn't there yet (🔴 *red*).
2. Write the **smallest** amount of code that makes it pass (🟢 *green*).
3. Tidy up the code without breaking the check (♻️ *refactor*).

Writing the check first is what makes the promise concrete. If you cannot turn a
criterion into a check, the criterion was too vague — that is signal, not failure.

## How This Applies to Your Project

Take **TASK-003** ("harden expense date handling"). Its criterion can be written as:

> **Given** the date field contains `" 2026-11-10 "` (with spaces around it),
> **When** I submit the form,
> **Then** the expense stored in `localStorage` has the date exactly `"2026-11-10"`.

That becomes the first failing test in `tests/expense.test.ts`. Only then do you
change `src/expense.ts` to trim the date — and the test turns green.

Same pattern for **TASK-004** ("don't lose an expense if saving fails"):

> **Given** the browser refuses to save (a storage error), **When** I submit,
> **Then** I see an error message and nothing crashes.

Here the test stubs `localStorage.setItem` to throw, and asserts the app survives —
that stub is the "Given" made real.

## Quick Reference Card

| Concept | Summary |
|---------|---------|
| Acceptance criterion | A promise shaped as *given / when / then*, pinned to one input and one result |
| Test | That promise as code that checks itself |
| Red → Green → Refactor | Failing check first, minimal code to pass, then tidy |
| Vague criterion | Cannot become a check → rewrite it until it can |
| Your sprint | Criteria live in the task list; their tests land in `tests/` before the code changes |
