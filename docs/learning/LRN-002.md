# Designing for testability

## Key Concepts

**Testability is a design property.** Where you put a rule decides how hard it is to
check later. Move a rule into the right spot today and the check becomes a one-liner;
leave it buried today and the check becomes a whole-screen simulation.

A **seam** is a natural joint in the code — a small standalone function, or an
injected dependency — where a test can plug itself in. Good seams come from keeping:

- **rules in plain functions** (no screen required), and
- **the screen thin** (wiring and display only).

## How This Applies to Your Project

- `src/expense.ts` already exposes `validateExpense` as a standalone function — a
  seam. REQ-002's checks call it directly (given `" 2026-11-10 "` → trimmed) instead
  of driving the form.
- `src/storage.ts` reads and writes `localStorage`. REQ-001 needs to test a *failing*
  save, so storage access should stay behind one small module whose behaviour a test
  can stub (make `setItem` throw) without rendering anything.
- `src/pages/AddExpense.tsx` builds the id today. REQ-003 wants id generation testable
  without a secure context — pulling a `newId()` function out lets a test stub
  `crypto.randomUUID` as undefined and call it directly.
- **Contrast:** if the trim/validate/id rules lived only inside `ExpenseForm.tsx`,
  every check would require rendering the form and simulating typing — brittle and slow.

## Quick Reference Card

| Concept | Summary |
|---|---|
| Seam | A small joint (function / injected dependency) where a test plugs in |
| Pure function first | Rules in plain functions; test them directly |
| Thin screen | Components do wiring + display, not decisions |
| Stub at the boundary | Test a failing save by stubbing the storage module, not the UI |
| Decide now | Restructuring for testability is cheapest at design time |
