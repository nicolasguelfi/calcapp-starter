# Test-first: the Red → Green → Refactor loop

## Key Concepts

TDD is one small loop you repeat:

- 🔴 **Red** — write a test for a behaviour that doesn't exist yet. It **fails**.
- 🟢 **Green** — write the **simplest** code that makes it pass.
- ♻️ **Refactor** — tidy the code; the test now guards you while you clean up.

The rule that makes it work: **no app code gets written unless a failing test is
asking for it.**

**The pitfall to avoid:** writing the screen first and *then* adding a test that
"matches what you built". That isn't TDD — the test is written to fit the code, so it
can never catch the code being wrong.

## How This Applies to Your Project

Take the save-failure message you just previewed. In TDD order:

1. **Red** — write a test: *given saving throws, when I add an expense, then the text
   "couldn't save" is visible.* It fails, because that message doesn't exist yet.
2. **Green** — add the message (and the guard so the save failure is returned, not
   thrown — see DEC-007). The test turns green.
3. **Refactor** — tidy the storage module; the test stays green.

Same shape for the load-failure notice: *given a failing read, when the dashboard
opens, then the "couldn't load" notice is shown — not the empty state.* The "Given"
is made real by **stubbing at the boundary** (a storage module whose `setItem` /
`getItem` throws), not by poking at the UI.

## Quick Reference Card

| Step | What you do |
|---|---|
| 🔴 Red | Write the failing test first — for behaviour that doesn't exist yet |
| 🟢 Green | The simplest code that makes it pass |
| ♻️ Refactor | Tidy up; the test keeps you safe |
| The rule | No app code without a failing test asking for it |
| Stub the boundary | Fake the failure (saving throws) instead of the UI |
